# ТЗ: Медицинский каталог — клиники, филиалы и публичные страницы

## 1. Цель

Необходимо реализовать систему управления профилями медицинских клиник и их филиалов с последующей публикацией в публичном каталоге.

Система должна обеспечивать полный цикл:

**Создание клиники → заполнение данных → добавление филиалов → предпросмотр → отправка на модерацию → проверка модератором → публикация → отображение в каталоге.**

При этом форма создания и публичная страница должны использовать единую структуру данных.

---

Система должна содержать следующие основные сущности:

1. **Клиника**
2. **Филиал**

4. **Направление**
5. **Услуга**
6. **Оборудование**
7. **Сертификат**
8. **Фотография**

```text

├── Специалисты

     │

     ├── Контакты
     ├── Режим работы
     ├── Направления
     ├── Услуги
     ├── Специалисты
     ├── Оборудование
     └── Фотографии
```

# 3. Статусы клиники

Клиника должна иметь следующие статусы:

| Статус              | Описание                              |
| ------------------- | ------------------------------------- |
| **Черновик**        | Клиника создаётся или редактируется   |
| **На модерации**    | Данные отправлены модератору          |
| **Нужны изменения** | Модератор вернул клинику на доработку |
| **Одобрена**        | Клиника прошла модерацию              |
| **Опубликована**    | Клиника доступна в публичном каталоге |

Основной сценарий:

```text
Черновик
   ↓
На модерации
   ↓
Одобрена
   ↓
Опубликована
```

При возврате:

```text
На модерации
   ↓
Нужны изменения
   ↓
Черновик
```

# 21. Режим работы

Для каждого дня недели:

```text
Понедельник  [09:00] — [18:00]
Вторник      [09:00] — [18:00]
Среда        [09:00] — [18:00]
Четверг      [09:00] — [18:00]
Пятница      [09:00] — [18:00]
Суббота      [09:00] — [18:00]
Воскресенье  Выходной
```

Для каждого дня предусмотреть:

* работает;
* выходной;
* круглосуточно.

Также предусмотреть возможность указать перерыв.

Например:

**09:00–13:00 / 14:00–18:00**

# 30. Публичная часть

## 30.1. Health Checker

Health Checker (проверка симптомов) используется как первоначальная точка взаимодействия пользователя с платформой.

### Сценарий

```text
Пользователь
     ↓
Health Checker
     ↓
Описание проблемы
     ↓
Уточняющие вопросы
     ↓
Предварительное направление
     ↓
Найти клиники
     ↓
Каталог с активным фильтром
```

ИИ должен формировать:

* предварительное медицинское направление;
* рекомендуемого специалиста;
* краткое объяснение.

Health Checker не должен позиционироваться как окончательная медицинская диагностика.

# 35. Связь данных создания и публичной страницы

Это ключевое техническое требование.

Каждое поле административной формы должно иметь конкретное назначение на публичной странице.

| Данные             | Использование               |
| ------------------ | --------------------------- |
| Название           | Карточка + страница клиники |
| Логотип            | Карточка + страница         |
| Описание           | Страница клиники            |
| История            | Страница клиники            |
| Миссия             | Страница клиники            |
| Направления        | Клиника + филиал            |
| Специалисты        | Клиника + филиал            |
| Оборудование       | Клиника/филиал              |
| Сертификаты        | Страница клиники            |
| Телефон            | Клиника/филиал              |
| Email              | Клиника/филиал              |
| Адрес              | Страница филиала            |
| Координаты         | Карта филиала               |
| Режим работы       | Филиал                      |
| Услуги             | Филиал                      |
| Фотографии         | Клиника/филиал              |
| Медицинский туризм | Дополнительная информация   |

Таким образом:

```text
              ЕДИНАЯ МОДЕЛЬ ДАННЫХ
                       │
          ┌────────────┴────────────┐
          ↓                         ↓
   Форма создания             Публичная страница
          │                         │
          └────────────┬────────────┘
                       ↓
                  Модерация
                       ↓
                   Публикация
```

# 36. Общие требования к Frontend

## Адаптивность

Все страницы должны работать на:

* Desktop (компьютер);
* Tablet (планшет);
* Mobile (мобильное устройство).

## Данные

Данные клиник, филиалов, врачей, услуг, цен, контактов и расписания должны поступать через API (программный интерфейс), а не быть прописаны непосредственно в коде.

## Состояния

Для каждого блока предусмотреть:

* Loading (загрузка);
* Empty State (нет данных);
* Error State (ошибка);
* успешная загрузка;
* отсутствие изображения;
* отсутствие отдельных контактных данных.

## Условное отображение

Если поле не заполнено, соответствующий блок **не отображается**.

Например, если нет Instagram:

```text
Instagram
```

не должен отображаться вообще.

То же самое применяется к:

* сайту;
* Telegram;
* WhatsApp;
* фотографиям;
* оборудованию;
* сертификатам;
* ценам;
* специалистам;
* режиму работы;
* дополнительной информации.

## 38. Что в итоге должен реализовать Frontend

Фронтенд фактически состоит из **трёх больших частей**:

1. **Личный кабинет клиники** — создание и редактирование данных.
2. **Модерационный сценарий** — статусы, ошибки и возврат на доработку.
3. **Публичный каталог** — Health Checker → каталог → клиника → филиал.
